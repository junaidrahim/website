## Seed 1: apprenticeship after code generation

### Claim to test

The first AI-native onboarding instinct was to teach tools and prompts. The journal suggests the durable curriculum may
instead be the older one: write down the problem, gather context, propose trade-offs, verify behavior, and own the
decision and production outcome. The essay must test this against what the interns actually experienced.

### Suggested beat map

These are structural beats, not section titles or prose:

1. One scene from the 2025 onboarding or app-a-thon where apparent implementation speed concealed either learning or a
   gap in understanding.
2. The pre-agent baseline from 2023: what Junaid believed made an intern grow into an engineer.
3. The conventional 2024 onboarding: teaching stack and culture through technical deep dives.
4. The 2025 intervention: why an AI-native bootcamp felt necessary, what it tried to teach, and what actually happened.
5. One tool-level success: AI review catching mechanical or language-specific issues and acting as a patient learning
   aid.
6. One failure or correction: tool-specific material aged, generated plans created noise, or fast output made
   thinking/ownership hard to observe.
7. The revised apprenticeship: what mentors now ask an engineer to make visible—problem model, evidence, decisions, test
   strategy, uncertainty, and responsibility.
8. What remains unchanged: builders still need to understand the system, make trade-offs, and answer for production
   behavior.
9. A falsifiable ending: how Junaid would judge whether the next cohort is becoming better engineers rather than only
   faster code producers.

### Evidence that would make it compelling

- The actual agenda/slides/recording from the 2025 session.
- One participant's project or PR before and after the program.
- Three short participant interviews, including one skeptical or negative account.
- One example of a tool or technique taught in 2025 that is obsolete by 2026.
- One skill from the 2023 note that participants say mattered more after AI adoption.
- A concrete description of what Junaid would change if running the program again.

### Failure condition

Drop this seed if there is no recoverable outcome evidence and no participant willing to be quoted or paraphrased with
permission. A memoir of the intended curriculum alone will not satisfy the challenge's preference for on-the-ground
detail.

## Seed 2: the repository has two audiences

### Claim to test

An internal SDK repository now serves people and agents, and within each group it serves maintainers and consumers. “Add
an instruction file” is not enough; the interface must route each audience to the right contracts, examples, errors, and
verification.

### Suggested beat map

1. A specific SDK/application failure caused by the agent using maintainer rules as consumer guidance, or vice versa.
2. The four audiences and the different questions each asks.
3. Why one large instruction file failed or became noisy.
4. The replacement: a short map, canonical contracts, generated agent docs, executable checks, and task-specific
   progressive disclosure.
5. How success was measured in review behavior or completed changes.
6. What this changed about internal platform/SDK engineering.

### Needed evidence

- A before/after agent task on the same repository.
- Instruction-adherence or failure-rate data.
- A public-safe example of generated docs staying aligned with CLI behavior.

## Seed 3: starting is cheap; finishing is scarce

### Claim to test

Parallel coding agents reduce the cost of beginning work faster than they reduce the cost of integrating it. The
consequential engineering system is an admission-control and closure loop, not a task launcher.

### Suggested beat map

1. A day with many running sessions and few integrated outcomes.
2. The shift from implementation queue to review/integration/decision queue.
3. Why familiar activity metrics become misleading.
4. A bounded work unit: explicit intent → isolated workspace → verification evidence → integration decision.
5. WIP limits, writer ownership, stop conditions, and stale-work cleanup.
6. Measure time to tested integration, rework, and abandoned attempts.

### Needed evidence

- Two weeks of task-level data from a named public project or an approved team.
- Started vs. integrated tasks, human review minutes, retries, abandoned branches, and elapsed time to a tested merge.

## Seed 4: review policy becomes executable

### Claim to test

AI can automate the lower review layers, but strategic review improves only when architectural judgment is expressed in
a form whose effect can be evaluated.

### Suggested beat map

1. The original review-pyramid observation on a greenfield Python service.
2. What the bot caught reliably and what it could not know.
3. The experiment with repository rules and technical opinions.
4. Why plausible comments are not proof that a review strategy was followed.
5. Turning review beliefs into structural tests, hooks, scenarios, and reviewer evals.
6. Which decisions remain human and why.

### Needed evidence

- Recover the Loom and rule changes.
- Replay a sample of historical PRs with and without the rules.
- Blind-label true issue, false positive, duplicated CI issue, and strategy-level issue.

## Seed 5: workspace, not agent, is the unit

### Claim to test

In a large monorepo, durable task state belongs to an isolated workspace rather than an agent session. Agents may come
and go; ownership, source state, environment, evidence, and integration history must persist.

### Needed evidence before an outline is worthwhile

- Normal checkout baseline.
- Workspace creation p50/p95, added disk, fetch volume, cold/warm build time, cache hit rate, and integration conflicts
  at 2/4/8/16 workspaces.
- One real task handed between agents without losing state.

## Do not lead with these framings

- Agent manager / manager of infinite minds.
- Software factory as a generic metaphor.
- Comprehension debt as a generic diagnosis.
- A tour of tools used in 2026.
- Productivity claims based on lines of code, token counts, self-reported time savings, or number of open PRs alone.

The organizer has already published richer versions of these. If one appears, it should support Junaid's first-hand
mechanism rather than become the thesis.
